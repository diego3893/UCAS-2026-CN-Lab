# 实验二 Socket 应用编程操作与验收指南

## 1 实验目标和最终成果

本实验要求使用 C 语言实现一个简单的 HTTP/HTTPS 文件服务器。程序需要同时监听 80 和 443 端口，并能处理多个并发连接。

最终需要形成两份成果：

1. 提交到 Online Judge 的 `02-socket.zip`。压缩包解压后必须有一个名为 `02-socket` 的目录，目录中只放编译所需的 C 源文件、头文件或 `include` 目录，以及原附件中的 `Makefile`。
2. 提交到课程网站的实验报告，建议命名为 `02-Socket编程实验报告.docx` 或 `02-Socket编程实验报告.pdf`。

服务器的核心行为如下。

| 入口 | 请求场景 | 必须返回的结果 |
| --- | --- | --- |
| HTTP，80 端口 | 任意合法 GET 请求 | `301 Moved Permanently`，并通过 `Location` 指向同一主机、同一路径的 HTTPS URL |
| HTTPS，443 端口 | 文件存在，未请求范围 | `200 OK`，响应体与文件内容逐字节一致 |
| HTTPS，443 端口 | 文件存在，带合法 `Range` | `206 Partial Content`，响应体为指定的字节范围 |
| HTTPS，443 端口 | 文件不存在 | `404 Not Found` |
| HTTP 和 HTTPS | 多个客户端同时访问 | 所有请求均能完成，服务器不能串行卡住、崩溃或漏响应 |

**完成实验的最低标准：**本地测试脚本退出码为 0，并且 OJ 最终显示“通过”。实验报告还必须给出足够证据，使读者能够确认每项功能确实通过，而不是只写“运行成功”。

## 2 先理解附件内容

### 2.1 课件与附件之间需要特别注意的差异

课件写的是 `h2 # python3 test/test.py`，但当前压缩包中的实际路径是 `02-socket/test.py`。如果从 `02-socket` 目录启动 `topo.py`，应执行：

```bash
h2 python3 test.py
```

`test.py` 的第一项请求设置了 `allow_redirects=False`，它直接检查 HTTP 响应是否为 301。后面的若干请求虽然 URL 仍写成 `http://10.0.0.1/...`，但允许自动跟随重定向，因此最终会到 HTTPS 端口检查 200、404 和 206。正确实现仍然应该让 80 端口统一返回 301，不能让 80 端口直接提供文件。

## 4 程序设计

### 4.1 推荐的线程结构

建议采用以下结构：

1. `main` 初始化 OpenSSL，创建共享的 `SSL_CTX`，加载 `keys/cnlab.cert` 和 `keys/cnlab.prikey`。
2. `main` 创建两个长期运行的监听线程。一个监听 80 端口，一个监听 443 端口。
3. 每个监听线程在循环中执行 `accept`。每接受一个连接，就为该连接创建一个工作线程，并立即回到 `accept`。
4. 工作线程只处理自己的连接。80 端口工作线程生成 301；443 端口工作线程为该连接创建独立的 `SSL *`，完成 TLS 握手后处理 GET 请求。
5. 工作线程发送完响应后释放 `SSL *`、关闭客户端套接字并释放线程参数。工作线程可设置为 detached，避免长期积累未 `join` 的线程资源。
6. 主线程等待两个监听线程，保证进程持续运行。

**为什么这样设计：**“两个监听线程”保证 80 和 443 同时工作；“每连接一个工作线程”保证慢客户端不会阻塞后续请求。只为每条连接创建独立的 `SSL *`，可以避免并发连接共享 TLS 会话状态。

**实现时必须避免：**不要把监听循环中的局部变量地址直接传给线程。应为线程参数分配独立内存，工作线程取走后释放，否则多个线程可能读到同一个已变化的文件描述符。

### 4.2 监听套接字的实现顺序

80 和 443 的监听线程都按以下顺序执行：

1. `socket(AF_INET, SOCK_STREAM, 0)` 创建 TCP 套接字。
2. 设置 `SO_REUSEADDR`。
3. 用 `htons(80)` 或 `htons(443)` 填写端口，地址使用 `INADDR_ANY`。
4. `bind` 绑定地址。
5. `listen` 开始监听。
6. 循环调用 `accept`，每个连接交给新的工作线程。

**为什么设置 `SO_REUSEADDR`：**服务器刚退出时，连接可能仍处于 `TIME_WAIT`。允许地址复用可以避免反复调试时出现 `Address already in use`。

**为什么使用 `htons`：**端口字段需要网络字节序。x86 主机通常使用小端序，直接赋值会导致端口解释错误。

**此时收集：**启动服务器后记录：

```bash
h1 ss -lntp | grep -E ':(80|443)[[:space:]]'
```

证据中应同时出现 80 和 443 的监听项。

### 4.3 正确接收和解析 HTTP 请求

工作线程不能假定一次 `recv` 或 `SSL_read` 就能拿到完整请求。应重复读取并追加到缓冲区，直到遇到 `\r\n\r\n`、对端关闭、发生错误或超过预设的请求头大小上限。

解析时至少完成以下内容：

1. 从请求行解析方法、目标路径和 HTTP 版本。
2. 只处理 `GET`。对于其他方法，可以返回 405，虽然附件测试没有显式检查。
3. 从头部中查找 `Range:`，字段名比较最好不区分大小写。
4. 去掉 URL 中的查询字符串，再把 URL 路径映射到当前目录中的文件路径。
5. 拒绝包含 `..` 等目录穿越成分的路径，避免客户端读取实验目录之外的文件。
6. 将 `/` 映射为 `/index.html`，方便浏览器直接访问根路径。

**为什么必须寻找 `\r\n\r\n`：**HTTP 每个头部行以 `\r\n` 结束，头部和响应体之间还要额外一个 `\r\n`。只按 `\n` 拼接或漏掉空行，`requests` 和浏览器可能无法识别响应。

**为什么不能只读一次：**TCP 是字节流，不保留应用层消息边界。一个 HTTP 请求可能被拆成多个 TCP 段。

### 4.4 80 端口返回 301

80 端口需要保留原请求路径，构造类似下面的响应：

```http
HTTP/1.1 301 Moved Permanently
Location: https://10.0.0.1/index.html
Content-Length: 0
Connection: close


```

实际主机部分应优先取请求中的 `Host` 字段；在本实验拓扑中测试程序要求 `/index.html` 的 `Location` 精确等于 `https://10.0.0.1/index.html`。不要错误地把 `:80` 或 `:443` 加入该字符串。

**为什么这样做：**301 用来把不加密的入口统一迁移到 HTTPS。`Content-Length: 0` 和 `Connection: close` 明确告诉客户端响应已经结束。

### 4.5 443 端口完成 TLS 握手

每条 HTTPS 连接按以下顺序处理：

1. `SSL_new(ctx)` 创建该连接的 TLS 对象。
2. `SSL_set_fd(ssl, client_fd)` 关联已接受的套接字。
3. `SSL_accept(ssl)` 完成服务端握手。
4. 使用 `SSL_read` 接收 HTTP 请求。
5. 使用循环 `SSL_write` 发送完整的响应头和响应体。
6. 结束时调用 `SSL_shutdown`，然后 `SSL_free`，最后关闭套接字。

**为什么不能共享一个 `SSL *`：**每条 TLS 连接都有自己的握手状态、密钥和读写状态。多个线程共享同一个连接对象会导致数据错乱。

**建议的健壮性处理：**进程启动时忽略 `SIGPIPE`，并对每一步检查返回值。客户端提前断开时，服务器应结束该工作线程，而不是让整个进程退出。

### 4.6 返回 200 和文件内容

若目标文件存在且没有 `Range`：

1. 用二进制方式打开文件。
2. 使用 `stat`、`fstat` 或移动文件指针得到准确大小。
3. 返回 `HTTP/1.1 200 OK`。
4. 在头部写入准确的 `Content-Length`、合适的 `Content-Type` 和 `Connection: close`。
5. 循环读取文件并循环发送，直到已发送字节数等于文件大小。

**为什么要循环发送：**`send` 和 `SSL_write` 都允许只写入部分数据。把一次调用的返回值当成“全部发送完成”会在大文件或并发条件下截断响应。

**为什么要逐字节验证：**状态码 200 只能证明服务器做出了响应，不能证明文件没有被截断、替换或多发字节。

### 4.7 返回 404

若路径不存在、不是普通文件或路径非法，返回 `404 Not Found`。响应应包含合法的 `Content-Length`，正文可以是简短文本或 HTML。

**为什么仍要写完整头部：**客户端需要知道 404 响应何时结束。状态行正确但长度错误，仍可能导致测试超时。

### 4.8 返回 206 和字节范围

附件至少测试两种形式：

```text
Range: bytes=100-200
Range: bytes=100-
```

处理流程如下：

1. 取得文件总长度 `total`。
2. 解析起始位置 `start` 和可选结束位置 `end`。
3. 对 `bytes=100-200`，起点为 100，终点为 200，二者都包含在响应内，因此长度为 `200 - 100 + 1 = 101`。
4. 对 `bytes=100-`，终点为 `total - 1`，长度为 `total - 100`。
5. 必要时把过大的结束位置截到 `total - 1`。
6. 使用 `fseek` 或 `lseek` 定位到 `start`，只发送计算出的范围长度。
7. 返回 `206 Partial Content`，并至少包含：

```http
Content-Range: bytes 100-200/文件总长度
Content-Length: 101
Accept-Ranges: bytes
```

无效范围建议返回 `416 Range Not Satisfiable`，并带上 `Content-Range: bytes */文件总长度`。这不是附件显式测试项，但能提高隐藏测试下的稳定性。

**为什么最容易出错：**HTTP 范围的结束下标是包含式的，所以计算长度必须加 1。少加 1 会导致响应体、`Content-Length` 和预期数据都不一致。

### 4.9 错误处理和清理

对 `socket`、`setsockopt`、`bind`、`listen`、`accept`、OpenSSL 初始化、文件打开和读写都检查返回值。错误日志应包含失败阶段和 `errno` 或 OpenSSL 错误信息。

调试时如果 `printf` 没有立即显示，可在关键输出后调用 `fflush(stdout)`。最终版本不要在每个数据块上打印大量日志，否则并发测试会受到终端 I/O 干扰。

每个工作线程退出前都要释放自己拥有的文件、`SSL *`、客户端套接字和参数内存。监听套接字和 `SSL_CTX` 由创建它们的长期线程或主线程管理。

## 6 在 Mininet 中运行

### 步骤 1 启动拓扑

必须在 `02-socket` 目录执行：

```bash
sudo python3 topo.py
```

如果课程镜像只为 `python` 配置了 Mininet，则按课件使用 `sudo python topo.py`。

**为什么需要 sudo：**Mininet 创建网络命名空间和虚拟链路需要超级用户权限。服务器监听 80 和 443 这两个特权端口也需要相应权限。由 sudo 启动的 Mininet 主机命令通常具有足够权限。

### 步骤 2 验证拓扑连通性

在 Mininet 提示符下执行：

```text
mininet> net
mininet> h1 ip addr show
mininet> h2 ip addr show
mininet> h2 ping -c 3 10.0.0.1
```

期望看到 `h1` 为 `10.0.0.1`、`h2` 为 `10.0.0.2`，且 ping 无丢包。

**为什么先测连通性：**如果二层或 IP 连通性本身失败，HTTP 超时不能归因于服务器代码。

**此时收集：**记录两端 IP、3 次 ping 的发送数、接收数、丢包率和往返时延摘要。

### 步骤 3 在 h1 启动服务器

```text
mininet> h1 ./http-server > ../evidence/server.log 2>&1 &
mininet> h1 ss -lntp | grep -E ':(80|443)[[:space:]]'
```

如果出现 `Permission denied`，确认程序是否在 Mininet 主机内以 root 身份运行。如果出现 `Address already in use`，先检查是否已有旧进程：

```text
mininet> h1 ps -ef | grep http-server
```

正常结束旧进程后再启动。代码中应已设置 `SO_REUSEADDR`，避免 `TIME_WAIT` 影响快速重启。

### 步骤 4 运行官方测试

```text
mininet> h2 sh -c 'python3 test.py > ../evidence/test.log 2>&1; rc=$?; cat ../evidence/test.log; echo EXIT_CODE=$rc'
```

期望没有 `AssertionError` 或其他异常，并看到 `EXIT_CODE=0`。测试脚本成功时本身不会打印“通过”，所以退出码是必须保存的数据。

## 7 逐项手工验证和数据采集

自动脚本只告诉你断言是否通过。实验报告需要更直观的状态码、头部和内容一致性证据。

### 7.1 HTTP 301

```text
mininet> h2 curl -sS -i --max-redirs 0 http://10.0.0.1/index.html
```

记录：状态码、`Location`、`Content-Length`。期望 `Location` 为 `https://10.0.0.1/index.html`。

### 7.2 HTTPS 200 和内容一致性

```text
mininet> h2 curl -k -sS -D ../evidence/https-200.headers https://10.0.0.1/index.html -o ../evidence/downloaded-index.html
mininet> h2 cmp index.html ../evidence/downloaded-index.html
mininet> h2 wc -c index.html ../evidence/downloaded-index.html
mininet> h2 sha256sum index.html ../evidence/downloaded-index.html
```

记录：状态码、声明的 `Content-Length`、源文件字节数、下载文件字节数、两个 SHA-256 值、`cmp` 退出状态。两份文件必须完全相同。

### 7.3 子目录文件

```text
mininet> h2 curl -k -sS -D ../evidence/dir-200.headers https://10.0.0.1/dir/index.html -o ../evidence/downloaded-dir-index.html
mininet> h2 cmp dir/index.html ../evidence/downloaded-dir-index.html
```

记录：状态码和 `cmp` 结果。此项证明程序根据 URL 查找真实文件，而不是硬编码根目录内容。

### 7.4 404

```text
mininet> h2 curl -k -sS -i https://10.0.0.1/notfound.html
```

记录：状态码、响应体长度和服务器在该请求后是否仍正常运行。

### 7.5 固定结束位置的 Range

```text
mininet> h2 curl -k -sS -D ../evidence/range-100-200.headers -H 'Range: bytes=100-200' https://10.0.0.1/index.html -o ../evidence/range-100-200.bin
mininet> h2 dd if=index.html of=../evidence/expected-100-200.bin bs=1 skip=100 count=101 status=none
mininet> h2 cmp ../evidence/expected-100-200.bin ../evidence/range-100-200.bin
mininet> h2 wc -c ../evidence/range-100-200.bin
```

记录：206、`Content-Range`、`Content-Length=101`、实际收到 101 字节、`cmp` 一致。

### 7.6 开放结束位置的 Range

```text
mininet> h2 curl -k -sS -D ../evidence/range-100-end.headers -H 'Range: bytes=100-' https://10.0.0.1/index.html -o ../evidence/range-100-end.bin
mininet> h2 dd if=index.html of=../evidence/expected-100-end.bin bs=1 skip=100 status=none
mininet> h2 cmp ../evidence/expected-100-end.bin ../evidence/range-100-end.bin
mininet> h2 wc -c index.html ../evidence/range-100-end.bin
```

记录：文件总长度、期望范围长度 `总长度 - 100`、实际范围长度、`Content-Range` 和 `cmp` 结果。

### 7.7 TLS 证书和握手

```text
mininet> h2 sh -c "echo | openssl s_client -connect 10.0.0.1:443 -servername 10.0.0.1 2>&1 | tee ../evidence/tls-handshake.log"
```

记录：是否完成握手、协商出的 TLS 版本和 cipher、证书 subject/issuer。证书是自签名证书，因此浏览器或工具提示“不受信任”并不等于握手失败，curl 测试需要 `-k`，Python requests 测试使用 `verify=False`。

### 7.8 并发处理

先做一个可重复的压力样例，例如总计 50 个请求、并发度 10：

```text
mininet> h2 sh -c "seq 1 50 | xargs -P10 -I{} curl -ksS --max-time 2 -o /dev/null -w '%{http_code}\n' https://10.0.0.1/index.html | tee ../evidence/concurrent-status.txt | sort | uniq -c"
```

再确认服务器仍在监听，并重新执行一次官方测试：

```text
mininet> h1 ss -lntp | grep -E ':(80|443)[[:space:]]'
mininet> h2 python3 test.py
```

记录：总请求数、并发度、200 数量、非 200 数量、超时数、测试后进程是否存活。理想结果为 50 个 200、0 个失败、服务器仍监听两个端口。

**为什么必须单独测并发：**官方附件的普通断言主要覆盖功能。课件和 OJ 还明确要求多流并发，串行服务器可能通过少量顺序请求，却在隐藏并发测试中超时。

## 12 常见故障定位顺序

### 无法启动服务器

1. 看 `server.log`。
2. 检查当前目录是否有 `keys/cnlab.cert` 和 `keys/cnlab.prikey`。
3. 检查是否以足够权限监听 80 和 443。
4. 用 `ss -lntp` 和 `ps -ef` 排查旧进程。
5. 确认设置了 `SO_REUSEADDR`。

### 客户端超时

1. 先 ping h1，排除拓扑问题。
2. 检查两个端口是否监听。
3. 查看服务器是否卡在一次不完整的请求读取上。
4. 检查响应是否含空行 `\r\n\r\n`。
5. 检查 `Content-Length` 是否等于真正发送的字节数。
6. 检查发送循环是否处理了部分写入。

### HTTPS 握手失败

1. 检查证书和私钥路径是否以程序当前目录为基准。
2. 检查证书和私钥是否匹配，以及加载函数返回值。
3. 用 `openssl s_client` 获取具体握手错误。
4. 确认每条连接新建自己的 `SSL *`。

### 官方脚本出现 AssertionError

按 `test.py` 中断言顺序定位：先检查 301 和 Location，再检查 HTTPS 200 和内容，随后检查 404、固定范围 206、开放范围 206。每次修复后重新运行全部测试，因为局部修改可能影响其他状态码。
